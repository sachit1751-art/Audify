# Audify 1.9.3 — Release notes draft

> **Status: production builds verified; unpublished draft pending final device review.** The four Android release APKs have been built and signed with the existing approved identity. The platform checklist below still distinguishes build/test verification from physical-device validation.

Audify 1.9.3 is planned to make everyday browsing and playback feel more responsive, personal and predictable, with platform-appropriate controls across supported devices.

## What's planned

- **Play Next by swiping:** Swipe a track row to place it immediately after the currently playing track. The existing preference continues to choose between Play Next and adding to the queue.
- **Elastic pull-to-refresh:** Home, Explore and Library follow the user's pull with an elastic refresh interaction and visible refresh feedback.
- **A Home layout of your own:** On Android phone/tablet and Android TV, reorder, hide and restore recommendation rows. Hidden rows are removed before client-side Home processing and presentation; eligible dedicated shelf requests are skipped. The provider's personalised Home endpoint is an aggregated response and still transfers its own shelf payload, which Audify cannot selectively omit at request time.
- **Smoother lists:** Keep stable row identity and avoid unnecessary row work during scrolling.
- **Artwork instead of motion artwork:** Choose static cover art instead of looping video artwork where animated cover art is supported.
- **Lyrics navigation:** Selecting another track from the lyrics panel returns the player to Now Playing so the new track's context is clear.
- **Skip-button feedback:** Previous and Next controls respond with a short press-and-kick animation, respecting reduced-motion preferences.
- **Theme Studio:** Build a custom palette with a live preview and direct colour controls.

## Platform availability checklist

These interactions must be adapted to each platform rather than copied literally. Touch-only gestures are not appropriate for a TV remote, watch crown or Android Auto driving interface.

| Platform | Required user-facing equivalent | Release gate |
| --- | --- | --- |
| Android phone and tablet | Full touch UI, Home editor, elastic refresh, swipe-to-Play-Next and player/lyrics interactions | Build, unit tests, emulator and tablet layout verification |
| Android TV / Google TV | D-pad accessible Home row ordering/visibility controls, stable shelf loading, remote refresh action, artwork preference and focus-safe player feedback | Home editor and refresh action implemented locally; TV build/tests and real remote-navigation verification still required |
| Wear OS | Watch-sized playback controls with press/kick feedback that respects the system animator scale; no phone-style Home editor or pull gesture | Skip-control press/kick animation implemented locally; Wear build/tests and watch/emulator verification still required |
| Android Auto | Keep the driver-safe MediaLibrary browsing and playback actions stable; do not add touch gestures, custom Home editing or decorative animations to the car surface | MediaLibrary tests and Android Auto host validation |
| Windows desktop | Keyboard/mouse equivalents for queueing and refresh; persistent Home layout, static artwork preference and track-aware lyrics navigation remain to be implemented or verified | Desktop parity is not complete; desktop CI/build and manual keyboard/mouse verification still required |

## Known scope boundaries

- Android Auto exposes a Media3 media library, not the phone's Compose Home screen. It should retain a concise, driver-safe browse hierarchy rather than expose the phone's layout editor or gesture interactions.
- The Windows desktop client is a separate Rust/GPUI application with its own versioning and release pipeline. Android version 1.9.3 does not automatically version or update that client.
- A platform is not considered complete merely because a shared model compiles. Each platform needs an accessible entry point and a passing platform-specific verification run.
